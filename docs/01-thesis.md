# 01 · 立项论证

> 本文回答「为什么要做 GCB、凭什么成、边界在哪里」。实现细节见 docs/02–05；
> 每个具体技术选择的理由见 docs/03（ADR）。本文不随里程碑更新，是长期共识底座。

## 0. 一句话主张

做一个**内网自部署、强类型、关系感知**的 web 游戏配置平台：
编辑体验保留 Excel 的肌肉记忆，语义却是数据库记录集；校验从导表时前移到击键时；
导出能力对标 Luban（json / lua / c#）。

## 1. 问题域：游戏配置工作流的五个真实痛点

1. **编辑体验断层**。数据在 Excel 里编辑，schema 在代码或 Wiki 文档里描述，两套真相永不重合。策划靠记忆力与口口相传维持类型正确。
2. **校验时点滞后**。错误在跑完一遍导表后以堆栈形式暴露，再由人肉反查到某表某行某列。返工半径以「分钟级导表 + 游戏重启」计。
3. **关系导航缺失**。FK 在单元格里只是一个数字，人脑充当指针解引用器。「这个奖励包到底给了什么」= 连续翻 3~5 次表。
4. **导出黑盒**。自研导表器无人敢改，作者离职即考古现场；导出错了不知道为什么，对了也不知道为什么。
5. **协作与保密**。配置是核心资产，Google Sheets 类 SaaS 在国内游戏公司不可达也不可接受；Excel 文件传来传去没有版本真相。

## 2. 对标拆解

| 方案 | 本质 | 解决了 | 留下了 |
|---|---|---|---|
| tabtoy | 表格化 schema + 多语言导出 CLI | 导出正确性、性能档（预生成代码） | 嵌套类型靠竖线编码字符串；编辑仍在 Excel；更新趋缓 |
| Luban (+LubanAssistant) | YAML schema + 校验 + 多 target 导出，国内主流 | 完备管线：类型系统、FK 校验、多语言、本地化 | 编辑仍在 Excel/WPS（详见 §2.1） |
| Excel + 自研导表 | 每家都写过一遍 | 定制贴合 | 维护者离职即死；无 schema 即无校验 |
| Airtable | SaaS 关系型表格 | 关系体验标杆：chip、表间跳转 | SaaS 不可达、数据出境、类型弱、无游戏侧导出 |
| Univer | 开源自部署的完整 Excel 复刻 | Excel 功能完整度、自部署 | 它复刻的恰是我们反对的（自由单元格模型，见 §4.1） |
| Unity ScriptableObject | 引擎内定制 | 定制自由 | 依赖重型引擎；策划不可编辑；表格场景笨拙 |

### 2.1 Luban 为什么没有解决这个问题（重点辨析）

Luban 是当前国内最接近的方案，必须诚实分析。它确认了「YAML schema + 强类型 + FK 校验 + 多语言导出」是正确地基——这也是 GCB 直接继承的地基。但它的编辑面仍然是 Excel：数据源是 xls/xlsx/csv 文件，校验发生在**运行导表命令时**。

Luban 生态的 [LubanAssistant](https://github.com/focus-creative-games/luban/wiki)（官方 VSTO Excel 插件）说明官方意识到了编辑问题，并提供了一定的 ref 跳转辅助。但 VSTO 插件被 Excel 的框架锁死：

- 仅 Windows + 完整 Office 可用（WPS、浏览器、Mac 均不可），每台策划机各装一遍，版本地狱；
- 没有跨表**反向引用**（「哪些表的哪些行引用了这行」需要全量索引，Excel 插件拿不到）；
- 没有层叠 peek / 面包屑式数据链钻取；
- 嵌套 `list<struct>` 仍是竖线编码或多 sheet 约定；
- 校验仍在导出时，不是编辑时。

**结论（本论证的核心命题）**：关系导航不是「没人想做」，而是**在 Excel 的框架内做不彻底**。schema 必须成为编辑器的运行时一等公民——编辑器认识类型系统、持有全量索引、能在每次击键后求值规则。这只有 web 原生编辑器能做到。导出器与校验器赛道已经饱和（tabtoy/Luban 都能做对），**编辑器赛道是空白**。

## 3. 差异化三叉戟

### 3.1 编辑时校验——架构代差，不是功能差距

命令行工具的校验模型是批处理：全量跑完才知道第几行炸了。web 常驻编辑器的模型是事件驱动：击键 → debounce → **只重算受影响的规则** → 单元格红点 + 行内中文消息。

这把错误发现半径从「分钟级导表 + 重启」压缩到「秒级」。关键论断：**Luban 无法通过加功能追上这一点**——它的编辑面（Excel）不是它的进程，它没有常驻编辑面。这是架构代差，是本项目相对 tabtoy/Luban 最值得投资的方向（实现要点：同构校验引擎 + 增量规则求值，见 docs/02 §2 与 docs/04 §5.6）。

### 3.2 FK chip + 层叠 peek——数据链导航

FK 单元格渲染为 chip（显示目标行 `displayField` 摘要 + 主键），点击弹出右侧 peek 抽屉；抽屉内可继续点击 FK 钻取；顶部面包屑显示当前数据链。Unity Inspector 的体验，但不占据整个屏幕，且可无限层钻取。策划的「翻表」操作从 5 次变 2 次点击。

### 3.3 反向引用面板——删除安全网

行详情列出「被哪些表的哪些行、经哪个字段引用」。策划删一个道具前立刻看到它被哪个商店、哪个任务引用。实现成本极低（一张倒排索引表，docs/04 §9），感知价值极高——几乎没有现成工具做这件事，因为纯导出器没有全量常驻索引，Excel 没有 schema。**这是低成本高感知的杀手级功能**。

三叉戟的共同前提：schema 是运行时一等公民 + 全量索引常驻。这再次指向 §2.1 的核心命题。

## 4. 产品决策论证

### 4.1 记录集语义，不复刻 Excel

放弃：自由单元格、合并单元格、任意格间公式、跨表引用。保留：网格、键盘流操作、拖拽填充、区域复制粘贴、撤销重做。

论证：配置数据的本质是**有类型的记录集**。Excel 的自由度恰是错乱之源——一次错位粘贴可以毁掉一整列而无人察觉；合并单元格让「一行=一条记录」的假设破产。Univer/Luckysheet 路线的全部工程量都花在复刻这些危险自由度上。放弃它们不是功能缺失，是**正确性保证**：任何时刻，文件里的每个值都能对照 schema 说出自己的类型与规则。

### 4.2 不做公式引擎

派生列（「最终价格 = 基础 × 系数」）克制地做：schema 声明表达式、单元格只读、导出时物化。完整的引用重算引擎（依赖图、脏标记、循环检测、增量重算）是工程量黑洞——Airtable 与 Univer 各自投入了数年。游戏数值的推导需求交给导出后的物化与游戏内工具，不进编辑器。

### 4.3 渲染路线：DOM 虚拟滚动，不用 canvas

工作负载测算：游戏配置表是 10²–10⁵ 行量级（不是 10⁶）。窗口化渲染下实际 DOM 节点只有可见区（约 40 行 × 30 列 ≈ 1200 个），固定行高 + overscan 的虚拟滚动在 Svelte（无 VDOM、编译期优化、外科手术式更新）下有充分余量。

选择 DOM 而非 canvas 的决定性理由：

1. **编辑体验是产品本质**（§3 全部论证）。IME 中文输入、下拉选择器、chip、无障碍，在 DOM 是原生能力；在 canvas 全是手动画布代码（文本度量、DPR 缩放、裁剪、命中测试、自制输入法浮层）。策划天天打中文，IME 是最高频路径。
2. **可测试性**：DOM 选择器断言 + Playwright，远比 canvas 截图金样可靠。
3. **对 GLM-5.3-FLASH 的可执行性**：HTML/CSS 标记是弱模型最可靠的领地；canvas 绘制代码出错率高且黑盒难调试。

护栏（写入验收，非口头承诺）：v1 固定行高（变高行是 DOM 虚拟滚动的头号杀手）；行级渲染块、不做每单元格组件；性能预算数字化——**10 万行 × 30 列滚动 60fps、滚动期无 >50ms 长任务**，作为 Playwright 测试在 M6 就锁定。升级路径保留：内核与渲染分离（docs/02 §4），极端需求出现时可在同一内核接口后更换渲染器。

### 4.4 自研网格的范围控制

自研成立的前提是把范围钉死在「记录集网格」而非「表格引擎」。OUT 清单：公式、合并单元格、自由布局、行内图表、打印分页。有了 OUT 清单，这是一个有界问题（虚拟滚动 + 选择模型 + 键盘状态机 + 编辑提交协议 + 自定义单元格渲染），而不是无底洞。

## 5. 路线排序辨析：「存储优先」还是「导出器先行」？

（本节回应立项讨论中的质疑：「难道关系型数据表、存储不是优先级最高吗？」）

**质疑中正确的部分**：数据平台（schema IR + 存储 + 校验引擎）确实是万物地基，没有任何功能可以绕过它。本路线图把它完整地放在 Phase 1 的最前面（M1–M3），一分不减。

**「先做导出器」的真实含义**：不是跳过存储，而是给数据平台选一个**最小但完整的消费者**当验收器——CLI。理由：

1. **导出正确性是一切信任的来源**。团队切换配置管线的决策依据是「导出物对不对」，不是「编辑器炫不炫」。Phase 1 结束时即使编辑器烂尾，也已经是一个可用的 Luban 替代品——失败率逐级可控。
2. **UI 建立在想象中的 API 上必然返工**。先写编辑器，等于在数据平台接口未定型时消费它；接口随实现演进时 UI 全部重写。
3. **编辑器（尤其自研网格）是全项目最高不确定度的部件**，必须在低风险部件冻结后再攻。

**对质疑的最终回应**：这不是「存储 vs 导出器」二选一——存储与校验在 Phase 1 前半段构建，导出器只是它们的第一个消费者与验收器。真正被否决的替代方案是「先做编辑器」，而它在依赖上不成立。为了尽早让数据「看得见摸得着」，M7 完成后网格 playground 即以只读方式加载 Phase 1 的示例数据（不需要 server），M8 接通真实读写。

## 6. 不做多人共同编辑 + 合并工具路线（已拍板）

**决策**：明确不做多人共编（实时协同编辑）。策划多人同时配同一张表的现实价值 ≈ 0——数值表通常由单一负责人维护，多人实时抢同一张表不是真实工作流，却会引入 CRDT/OT、冲突语义、测试面爆炸等最高量级的工程成本。

替代路径：

- **单人编辑 + 乐观并发护栏**：保存时校验行内容哈希（baseRowHash vs 当前行哈希），不一致则 409 拒绝并提示刷新。约 20 行代码，防同一人双开标签页静默覆盖。这是数据安全护栏，不是协作功能。
- **跨人合并走 git + 专用合并工具（Phase 3+）**：source of truth 是按主键稳定排序的 JSONL **文本**，行级 diff 天然可合并；SQLite 是派生索引、可随时重建，**合并工具完全不涉及数据库合并算法**。后期工具做「两份数据集的语义 diff（表/行/字段三级）+ 手动选边 + 落盘 + 重建索引」。

ws 的唯一保留用途是 Phase 3 热更推送（编辑器保存 → server 推送 → 游戏内热重载），server→游戏单向，与多人编辑无关。
